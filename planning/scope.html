정해지면 이 표의 해당 줄만 바꿉니다. v2.0: 최종 프로젝트 줄을 카드마다 더하고, 카드 열에 「검색」 · 「커뮤니티」를 더했습니다. v1.1: 카드 순서(① → ⑦ → 보완 → 공통)로 정렬했습니다. 설정값 = 값만 바꾸면 정책이 바로 반영되는 항목 (코드 수정 없음)

카드항목지금 쓰는 값
①자녀 프로필 수정 · 삭제수정은 자유, 삭제는 논리 삭제 (목록 · 상세 · 추천에서 제외). 주문은 당시 자녀 정보를 복사해 두어 영향 없음
①배송지회원당 여러 개 등록, 배송지가 있으면 기본 배송지는 정확히 1개 (없으면 0개). 기본 배송지는 삭제할 수 없음 (409) — 다른 배송지를 기본으로 바꾼 뒤 삭제. 화면이 목록에서 골라 주문 요청에 넣음 (경로는 8장)
①토큰 재발급 · 로그아웃Access Token(JWT, 30분, 업무 정보는 memberId · nickname · roles(BUYER · SELLER · ADMIN, 판매자 여부는 저장하지 않고 발급할 때 계산), 발급 · 만료 시각(iat · exp)은 기본 포함) · Refresh Token(14일, HttpOnly 쿠키). 재발급은 저장된 Refresh Token과 같을 때만, 재발급할 때마다 기존 Refresh Token 폐기. 로그아웃은 Refresh Token 폐기 (이미 발급된 Access Token은 만료까지 유효). 판매자 승인 뒤에는 재발급으로 최신 역할 반영
①인증 (최종)토큰 검증 · 무효화 확인 · 역할 검사 · CORS는 API Gateway만 함. Gateway가 밖에서 온 X-Member-*를 지우고 검증된 토큰의 X-Member-Id · X-Member-Roles · X-Member-Nickname을 붙임. 서비스는 Spring Security 없이 이 헤더로 로그인 회원을 앎(없거나 잘못되면 401). /admin/**는 ADMIN, /seller/**는 SELLER만 Gateway가 통과(토큰 없으면 401 · 역할 없으면 403). 토큰 무효화는 회원이 member.tokens-revoked로 알리고 Gateway가 받음 (판매자 자격을 잃으면 무효화)
①로그인화면이 카카오에서 받은 인가 코드를 POST /auth/login/kakao로 보내면, 처음이면 가입하고 토큰을 발급. 개발용 토큰 발급 POST /dev/tokens는 local · test · dev에서만 열림
①닉네임회원 정보 수정은 닉네임만 (중복 불가). 바꾸면 member.changed를 보내 판매자 신청의 신청자 이름에 반영
①자녀 정보 입력필수: 이름 · 생년월일 · 성별 · 키 · 몸무게 / 선택: 체형 · 선호 핏 (입력하지 않으면 null) · 키 · 몸무게는 소수 첫째 자리까지 (0.1cm · 0.1kg) · 체형은 SLIM(마름) · NORMAL(보통) · CHUNKY(통통), 선호 핏은 SLIM(딱 맞게) · REGULAR(보통) · LOOSE(여유) · 입력 범위: 이름 50자 이하, 키 40.0~200.0cm, 몸무게 2.0~150.0kg · 수정은 전체 값을 보내는 방식
①성장 이력에서 체형 비교체형이 비어 있을 수 있으므로 null → 값, 값 → null도 바뀐 것으로 보고 1건 쌓음
①②이벤트 값 목록child.changed gender: MALE · FEMALE, bodyType: SLIM(마름) · NORMAL(보통) · CHUNKY(통통), preferredFit: SLIM · REGULAR · LOOSE / product.changed status: SALE_PENDING(판매 시작 전) · ON_SALE · STOPPED, 옵션 saleStatus: ON_SALE · STOPPED, size는 문자열 (예: "110", 사이즈 없는 상품은 null), sizeFree로 사이즈 구분 없음 표시 (세미 제안 P10 반영)
②판매 상태상품은 판매대기(SALE_PENDING) → 판매중(ON_SALE) ⇄ 판매중지(STOPPED). 관리자가 멈춘 상품은 관리자만 다시 열 수 있음. 옵션 상태 값(판매중지 · 보관)은 있지만 세미에서는 모든 옵션이 판매중
②품절상태가 아니라 판매 가능 수량 0. 모든 옵션이 품절이어도 목록에 「품절」로 남고, 남은 수량은 5개 이하일 때만 보여 줌
②상품 수정판매대기 상품만 옵션 · 가격 · 실측 · 카테고리를 바꿈. 판매를 시작한 상품은 기본 정보와 정보 값만 바꿈
②가격옵션마다 저장하지만, 의류는 색상 · 사이즈가 달라도 상품 하나에 가격 하나
③추천 규칙자녀 키가 권장 키 범위 안에 드는 사이즈가 후보이고, 그런 사이즈가 없을 때만 범위 밖 2cm 이내 사이즈가 후보입니다. 후보가 둘 이상이면 범위 가운데가 키에 가장 가까운 사이즈(기준)에서 다음 순서로 고릅니다. ① 체형: 통통하면 한 단계 큰 쪽, 마르면 한 단계 작은 쪽 ② 체형이 보통이거나 키만으로 추천할 때는 선호 핏: 여유(LOOSE) → 한 단계 큰 쪽, 딱 맞게(SLIM) → 한 단계 작은 쪽, 보통(REGULAR) → 기준 사이즈 ③ 선호 핏을 입력하지 않았으면 후보가 둘일 때 큰 쪽, 셋 이상일 때 기준 사이즈 · 끝 사이즈에서는 더 옮기지 않음 · 사이즈 구분이 없는 상품(FREE)은 추천 없이 안내(SIZE_FREE)
③적합도자녀 키가 권장 키 범위의 어디에 있는지로 정합니다. 범위 아래쪽 끝에서 2cm 이내는 여유 있음(ROOMY), 위쪽 끝에서 2cm 이내는 작을 가능성 있음(TIGHT), 그 사이는 적정(PROPER)입니다(두 끝 구간이 겹치면 적정). 그다음 체형으로 한 단계 옮깁니다. 통통하면 작을 가능성 있음 쪽으로, 마르면 여유 있음 쪽으로 옮깁니다. 범위 밖 후보는 범위보다 작으면 여유 있음, 크면 작을 가능성 있음입니다. 키만으로 추천할 때와 범위 밖 후보는 체형으로 옮기지 않습니다
③몸무게 · 체형 사용 방식추천은 몸무게로 자녀의 체형을 판정합니다. 기준은 질병관리청 2017 소아청소년 성장도표의 신장별 체중이고, 성별 · 키별 15백분위 이하는 마름, 85백분위 초과는 통통, 그 사이는 보통입니다. 표는 성별과 연령 구간(0-23개월, 24-35개월, 3-18세)으로 고릅니다. 보호자가 체형을 입력했으면 판정 결과와 비교해, 같거나 한 단계 다르면 판정 결과를 쓰고, 두 단계 다르면(마름과 통통) 체형을 쓰지 않고 키만으로 추천합니다. 체형을 입력하지 않았으면 판정 결과를 그대로 씁니다 · 연령 구간 밖이거나 표에 없는 키면 판정하지 않고 입력한 체형을 씀 · 화면 안내 코드: 판정 결과로 바꿈(BODY_TYPE_ADJUSTED) · 키만 씀(HEIGHT_ONLY) · 체형 때문에 선호 핏과 다른 사이즈(PREFERRED_FIT_NOT_APPLIED)
③맞는 사이즈 없음자녀 키가 모든 사이즈의 권장 키 범위에서 2cm보다 멀 때 · 200 + recommendedSize: null + 안내 문구(NO_MATCHING_SIZE)
③없는 · 남의 · 삭제된 자녀회원 · 추천 모두 404 (추천은 child.changed 복사본의 memberId · deleted로 판단) · 사이즈 추천은 상품을 먼저 확인해 없으면 404 「상품을 찾을 수 없습니다.」, 자녀 세 경우는 같은 문구 「자녀를 찾을 수 없습니다.」
③자녀 맞춤 목록판매 중이고 추천 사이즈가 팔리는 상품, 최신 등록순. 사이즈 무관 상품은 팔 수 있는 옵션이 있으면 넣음. 카테고리 필터는 말단 카테고리로만 거르고, 묶음 카테고리(의류 · 잡화)로는 빈 목록. 카드에 적합도는 없음 → 최종: 홈 맛보기 4개는 AI 선택, 더보기는 활동 선호 점수 순 (아래 「홈 맛보기 4개」 · 「더보기 목록」 줄)
③사이즈 추천과 판매 상태사이즈 추천은 판매 상태 · 품절과 관계없이 계산하고, 맞춤 목록만 살 수 있는 상품으로 거름
③AI 추천 입력자녀 프로필(개월 수 · 키 · 몸무게 · 체형 · 선호 핏), 상품 복사본(이름 · 브랜드 · 설명 · 정보 값 · 사이즈별 실측), 활동 기록 최근 30일 50건, 구매 기록, 성장도표 · LMS 기준 데이터. 자녀 이름 · 생년월일 · 회원 ID는 외부 AI API에 보내지 않음
③활동 이벤트상품 상세 진입(화면이 추천 서비스에 기록, 자녀 ID 없음), 검색어(검색 서비스가 search.performed로 발행, 로그인 회원이 검색어로 찾은 첫 페이지만), 장바구니 담기(주문 서비스가 cart.item-added로 발행, 자녀 ID는 고른 경우만) · 빼기(cart.item-removed, 발행 요청), 주문 취소 중 구매자 취소. 노출 목록은 받지 않음
③추천 순위 계산활동 이벤트를 받을 때 자녀별 카테고리 · 브랜드 선호 점수를 갱신(카테고리 일치 +3, 담기 +2 추가, 브랜드 일치 +2, 등록 7일 안 +1. 숫자는 추천 규칙 문서). 더보기 목록은 그 점수로 정렬해 읽기만 함. 30일 지난 활동은 하루 한 번 제외
③더보기 목록연 순간의 순서를 끝까지 유지(1쪽 응답의 기준 시각을 2쪽부터 asOf로 보냄). 활동은 다음에 열 때 반영. 장바구니에 있는 상품과 같은 자녀에게 이미 산 상품은 뺌
③홈 맛보기 4개선호 점수 상위 20개를 후보로 AI가 4개와 이유를 고름. 자녀당 한 번 저장하고 입력이 바뀌거나 24시간이 지나면 다시 부름
③함께 사면 좋은 상품카테고리 짝 규칙(상의 ↔ 하의, 상의 · 하의 → 아우터, 의류 → 잡화) + 벡터 거리순 후보 20개 + 장바구니 판매자 가점 → AI가 4개와 이유
③AI가 고르는 범위사이즈는 상품의 실제 사이즈 목록 안에서만, 상품은 후보 목록 ID 안에서만(구조화 출력)
③규칙의 역할규칙 결과를 AI 입력으로 줌. AI 호출 실패 · timeout · 하루 상한 초과 때만 규칙 결과로 응답. 규칙이 AI 답을 바꾸지 않음
③근거응답 reasons(사이즈) · reason(상품) · source(AI 또는 RULE). 추천 DB에 입력 스냅샷 · 규칙 결과 · AI 결과 · 참고한 글 조각 id 저장
③이유 문장아이 몸을 평가하는 표현 금지, 옷 치수 기준으로만. 금지어에 걸리면 규칙 문장으로 대체
③하루 호출 상한서비스 전체 하루 횟수(설정값, 처음 2,000회). 넘으면 규칙 응답
③timeoutGateway 3초, 추천 서비스 내부 2.5초
③등록 취소 · 판매 중지 상품추천 복사본의 상태만 갱신, AI 입력으로는 유지, 결과에서만 제외(판매 중 조건을 조회 계층에 공통으로)
③비로그인 · 자녀 없음추천 목록 대신 로그인 · 자녀 등록 안내만. 상세에서 자녀를 고르지 않으면 「자녀를 고르면 추천해 드려요」
③탈퇴 · 자녀 삭제추천이 member.withdrawn을 받아 활동 기록 · AI 응답 삭제. 자녀 삭제는 child.changed(deleted)
④장바구니 수량 합치기 · 주문상품 나누기(회원 · 옵션 · 입을 자녀)가 같으면 한 줄로 수량을 합침 (한 줄 1~99개). 주문상품은 옵션 × 입을 자녀 1행, 배송은 판매자별 1건. 결제완료되면 주문한 장바구니 줄을 지움
④결제 제한 시간설정값 (지금 10분)
④중복 주문 방지POST /orders에 Idempotency-Key 헤더(UUID, 선택). 같은 키 · 같은 내용이면 처음 만든 주문을 200으로 돌려주고, 같은 키 · 다른 내용이면 409. 키가 없으면 지금처럼 매번 새 주문

공통결제 이벤트 보내기아웃박스: 업무와 같은 트랜잭션에서 메시지를 표에 저장하고, 릴레이가 1초마다 최대 100건을 id 순서로 kidly.payment.events에 보냄. 보낸 메시지는 7일(Kafka 보존 기간과 같음) 뒤 매일 4시에 지움. 안 보낸 메시지는 지우지 않음. 모두 설정값
공통결제 이벤트 받기구독 그룹 kidly.payment. 받는 토픽 kidly.member.events · kidly.order.events(판매자 부분 취소 포함) · kidly.settlement.events. 실패하면 1초 간격으로 3번 더 시도하고 {토픽}.payment.dlt로 보냄(eventType 헤더가 없으면 바로 DLT). 스위치: 회원 · 주문 수신 PAYMENT_KAFKA_CONSUMER_ENABLED(켬), 정산 수신 PAYMENT_KAFKA_SETTLEMENT_CONSUMER_ENABLED(dev 켬, prod는 정산 Kafka 발행이 main에 들어갈 때). 끄면 Spring 이벤트로 받음
공통주기 작업 · 서버 증설 (주문)주기 작업은 서버가 여러 대여도 한 대에서만 실행(DB advisory lock)하고, 대상이 많아도 이어서 끝까지 처리(순환 커서). 메모리 상태 · 세션이 없어 대수를 늘려도 중복 처리가 없음(Kafka 파티션 3개가 동시 처리 상한)
검색검색 조건요청 · 응답은 v1.1의 상품 목록과 같음: categoryId · keyword(50자 이하) · attributes(항목code:값ID, 20개까지) · sort(NEWEST · PRICE_ASC · PRICE_DESC) · page · size(1 ~ 100). 판매 중 상품만. 검색어는 상품명에서 찾고, 검색어의 형태소가 모두 들어 있어야 맞음. 같은 항목 안의 값은 하나만 맞으면 되고 항목끼리는 모두 맞아야 함
검색표시 가격 · 품절표시 가격 = 판매할 수 있는 옵션 중 최저가, 없으면 전체 옵션 중 최저가. 품절 = 모든 옵션이 품절일 때만. 상호명은 판매자 색인에서 붙임(없으면 null)
검색페이지 한계1만 건째 결과까지 보여 줌(Elasticsearch 한계). 전체 개수는 정확히 셈
검색색인 반영product.changed · seller.changed를 Kafka로 받아 색인(그룹 kidly.search). 같은 상품의 늦게 온 옛 이벤트는 발생 시각(occurredAt)을 버전으로 써서 Elasticsearch가 거절. 실패는 1초 간격 3번 더 시도 뒤 {토픽}.search.dlt. 처음 채우기는 상품 · 판매자의 전체 다시 보내기 API로
검색검색 장애Elasticsearch에 닿지 못하면 503 「검색을 쓸 수 없습니다」. 상품 DB로 대신 찾지 않음. 되돌릴 때는 Gateway의 검색 주소(KIDLY_SEARCH_URI)를 kidly-app으로 바꿔 상품의 기존 목록 API로 돌아감. 상품 상세 · 장바구니 · 주문은 영향 없음
검색검색어 이벤트로그인 회원이 검색어로 찾은 첫 페이지만 search.performed로 보냄(비로그인 · 둘러보기 · 다음 페이지 · 503은 보내지 않음). DB가 없어 아웃박스 없이 별도 스레드로 보내고, 실패하면 로그만 남기고 버림. 키는 회원 ID
커뮤니티리뷰구매확정(order-item.purchase-confirmed)을 받은 주문상품만 작성(남의 것 403), 주문상품마다 1개(409). 별점 1~5 정수, 본문 공백 제외 1~1,000자. 수정 · 삭제는 작성자만, 수정은 보낸 필드만. 닉네임은 작성 때 값을 저장(공개 목록에 회원 ID는 없음). 상품별 리뷰 수 · 별점 합은 같은 트랜잭션에서 원자적으로 증감, 평균은 소수 첫째 자리 반올림(없으면 null). 판매 종료 상품의 리뷰도 남김
커뮤니티찜회원 × 상품마다 1개(다시 찜해도 1개, 없는 찜 취소도 성공). 판매 중 · 품절 상품은 찜 가능, 판매 종료 · 복사본에 없는 상품(판매 시작 전)은 거절. 찜한 상품이 판매 종료되면 목록에 남기고 표시만 바꿈. 상품별 찜 수는 원자적으로 증감
커뮤니티판매 상태 표시판매 종료 = 상품이 판매 중이 아니거나 판매 중 옵션이 0개 · 품절 = 판매 중이고 판매 중 옵션이 모두 재고 없음 · 그 밖은 판매 중. 상품 복사본 기준이라 잠깐 늦을 수 있고, 실제로 살 수 있는지는 상품 · 주문이 판단
커뮤니티목록 · 탈퇴목록은 커서 방식(cursor · size 1~50, 기본 20, 마지막 쪽은 nextCursor: null). 탈퇴(예정, #663): 찜은 지우고 찜 수를 줄임, 리뷰는 남기고 작성자를 「탈퇴한 회원」으로 표시(K26)

제안 — 담당자 확인 후 채택 ​

아직 합의되지 않은 항목의 제안입니다. 해당 기능을 구현하기 전에 확인란의 담당이 합의하고, 채택하면 위 표로 옮기며 다른 안으로 정하면 이 줄을 고칩니다. P9 · P23은 채택돼 구현됐습니다.
