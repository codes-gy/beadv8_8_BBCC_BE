전체 그림 ​

3.1 전체 구성 ​

세미의 모듈러 모놀리스(앱 1개 · 배포 1개 · DB 1개)에서 출발해, 도메인 사이 이벤트를 Kafka로 옮기고 서비스를 하나씩 떼어 내고 있습니다. 모든 요청은 API Gateway를 거치고, 서비스끼리는 서로 부르지 않습니다.

  • 요청은 화면 → API Gateway(dev 8083 · prod 8084) → 서비스로 갑니다. Gateway가 토큰 검증 · 무효화 확인 · 역할 검사 · CORS를 하고 검증된 회원 정보를 헤더로 넘깁니다. 서비스는 Gateway 뒤에서만 열린다는 전제입니다.
  • Gateway는 경로별로 보냅니다: GET /api/v1/products → search-service, 자녀 경로 → childprofile-service(dev), 나머지 → kidly-app. 결제 · 추천도 분리를 마치면 경로를 그대로 둔 채 넘깁니다.
  • 도메인 사이는 Kafka 이벤트로만 주고받습니다(토픽은 3.3). 다른 도메인 정보는 이벤트로 받아 둔 복사본을 씁니다 (6.3).
  • 서버는 EC2 2대입니다: t3.large(Docker Compose: Gateway · kidly-app · 검색 서비스 · PostgreSQL · Kafka)와 t3.medium(k3s: Elasticsearch · 모니터링). 상품 이미지는 S3, 배포는 GitHub Actions가 맡습니다.
  • 검색 서비스(search-service)는 kidly-app과 따로 뜨는 Spring Boot 앱입니다. 앱 서버 t3.large의 docker compose에서 돌고(프로필 search, heap 512m), 서버 안 127.0.0.1:8082에만 열립니다.
  • Elasticsearch(공식 이미지 + nori)는 모니터링과 같은 t3.medium의 k3s에서 돕니다(namespace search, heap 1g, 데이터 10Gi). 검색 서비스는 VPC 안에서 NodePort 30920으로 붙고, 보안 그룹은 t3.large에서 오는 것만 받습니다.
  • 지금은 dev만 켜져 있습니다. 배포는 앱 배포 워크플로가 Elasticsearch를 먼저 올린 뒤 검색 서비스를 올립니다. Elasticsearch 설정이나 이미지가 바뀌면 다시 뜨는 동안 2분쯤 검색이 끊깁니다.

아래는 세미 때 구성(앱 1개 · EC2 1대)입니다. 참고로 남깁니다.

3.3 모듈 연결 지도 ​

도메인 사이 이벤트는 모두 Kafka로 갑니다. 보내는 도메인마다 토픽이 하나이고, 받는 도메인은 자기 구독 그룹으로 필요한 종류만 받습니다. 최신 연결은 도메인 연결 지도에서 볼 수 있습니다.

보내는 쪽토픽이벤트 → 받는 쪽 (구독 그룹 kidly.{받는도메인})
회원kidly.member.eventsmember.registered → 결제 · 알림 · member.changed → 판매자 · member.withdrawn → 자녀 프로필 · 결제 (추천 · 커뮤니티 예정) · member.tokens-revoked → Gateway
판매자kidly.seller.eventsseller.changed → 회원 · 상품 · 주문 · 추천 · 검색
자녀 프로필kidly.childprofile.eventschild.changed → 주문 · 추천
상품kidly.product.eventsproduct.changed → 주문 · 추천 · 검색 · 커뮤니티 · stock.deducted · stock.deduction-failed → 주문
주문kidly.order.eventsorder.created → 상품 · order.payment-requested → 결제 · order.cancelled → 상품 · 결제 · order-item.purchase-confirmed → 정산 · 추천 · 커뮤니티 · order-item.cancelled → 결제 · 상품 · cart.item-added → (추천 예정)
결제kidly.payment.eventspayment.completed · payment.failed → 주문 · payment.payout-completed · payment.payout-failed → 정산
정산kidly.settlement.eventssettlement.payout-requested → 결제 (dev 켬, prod는 main 반영 때)
검색kidly.search.eventssearch.performed → (추천 예정)
  • 결제 · 주문 · 정산 · 상품 · 커뮤니티에는 Spring 이벤트 수신 코드도 남아 있습니다. Kafka 수신 스위치를 끌 때 되돌아가는 길입니다. 판매자 부분 취소(order-item.cancelled)는 Kafka로만 받습니다.
  • 다른 도메인 정보가 필요하면 이벤트로 받아 자기 복사본을 둡니다 (6.3). 예: 추천은 자녀 정보 · 상품 사이즈 정보를, 주문은 자녀 정보 · 상품 가격을 복사본으로 가집니다.
  • 🕒 = 시간에 따라 실행되는 작업 (주문: 결제 제한 시간 만료 · 자동 구매확정 · 택배 조회 · 아웃박스 릴레이 / 정산: 영업일 일정산(Spring Batch) · 지급 결과 재요청 · 아웃박스 릴레이 / 결제: 충전 정리 · 주문 취소 환불 재처리 · 아웃박스 릴레이 · 정리 / 상품 · 자녀 프로필: 아웃박스 릴레이 / 알림: 메일 재발송 / 회원: 만료된 Refresh Token 정리)
  • 다른 모듈의 테이블은 직접 읽지 않습니다. 도메인 사이에는 FK를 두지 않고, 다른 모듈의 ID는 값으로만 저장합니다.

아래는 세미 때 그림(Spring 이벤트)입니다. 연결은 위 표가 기준입니다.

3.4 주문 전까지 ​

주문 · 추천은 회원 · 상품에 묻지 않고, 미리 받아 둔 복사본을 씁니다 (6.3). 실선 = 사용자 요청, 점선 = 이벤트. 그림은 세미 기준이고, 지금 점선의 이벤트는 Kafka로 갑니다(3.3).

3.5 구매에서 정산까지 ​

결제는 주문 · 상품을 부르지 않고, 받은 이벤트로만 움직입니다. 결제 결과 · 지급 결과는 지갑을 바꾼 트랜잭션에서 아웃박스에 저장한 뒤 보내므로 「돈은 빠졌는데 알림이 사라지는」 일이 없습니다.

실선 = 사용자 요청, 점선 = 이벤트. 번호 순서대로 7장의 ④ → ⑦ 카드가 이어집니다.

3.6 추천 서비스 데이터 흐름 ​

실선 = 사용자 요청, 점선 = Kafka 이벤트.

  • 주문 · 결제 경로에는 추천 서비스가 없습니다. 추천 서비스가 멈추면 Gateway가 3초 뒤 끊고 화면은 추천 영역만 비웁니다.
  • 계산은 이벤트가 올 때 합니다(복사본 · 임베딩 · 선호 점수). 요청이 올 때는 저장된 것을 읽고, AI 호출은 홈 맛보기와 함께 사면 좋은 상품에만, 같은 입력이면 저장된 응답을 재사용합니다.

3.7 결제 서비스 이벤트 흐름 ​

실선 = 요청 · 저장, 점선 = Kafka.

결제는 다른 도메인을 부르지 않습니다. 화면 요청(충전 · 조회)과 이벤트만 받고, 결과는 이벤트로만 알립니다. 그래서 결제를 다른 서비스로 떼어도 다른 도메인의 코드는 바뀌지 않습니다.

3.8 검색 서비스 흐름 ​

검색은 상품 DB를 읽지 않고 상품 · 판매자 이벤트로 색인합니다. 검색 서비스가 멈추면 상품 목록만 503이고, 상품 상세 · 장바구니 · 주문은 kidly-app이 받아 그대로 동작합니다.
