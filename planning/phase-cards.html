단계별 카드 ​

한 흐름을 7단계로 나누고, 각자 맡은 단계를 개발합니다.

v2.0: ③ 카드를 AI 추천 기준으로 바꾸고, ⑦ 카드에 정산 상세(⑦ 상세 1 ~ 10)를 더하고, 구매확정 뒤의 ⑧ 리뷰 · 찜 카드를 새로 넣었습니다. 다른 카드에는 최종에서 더한 API · 이벤트를 노란 바탕으로 적었습니다. 단계 사이 이벤트는 모두 Kafka로 갑니다.

v1.1: 단계 연결이 끝나 v1.0의 「혼자 시작하기」 칸과 7.1 「카드별 추가 데이터」는 뺐습니다. 시연은 7.1 초기 데이터로 ①부터 차례로 진행합니다.

카드 읽는 법 — 모든 카드가 같은 순서입니다. 카드 그림의 자녀 정보 칸과 추천 규칙은 2.1이 기준입니다 (그림은 ERD 확정 뒤 갱신). v1.1에서 카드 그림은 대부분 고치지 않았습니다. 그림과 표가 다르면 표 · 2.1 · 8장이 기준입니다. ERD를 다시 그릴 때 상품은 표 18개, 추천은 표 4개(+ 사이즈 줄 2개) 기준입니다 (상품 기획서 v6 10쪽, 추천 기획서 v3 9쪽).

목적이 단계가 끝나면 무엇이 되는가

받는 것 · 넘기는 것앞 단계와 다음 단계 사이의 약속 (이것만 지키면 각자 개발해도 맞물림)
만들 API이 단계의 화면이 부르는 API

① 회원 · 자녀 프로필 등록 ​

담당 maruhxn(회원) · codes-gy(결제: 지갑 생성) 목적 보호자가 카카오로 가입하고, 자녀 프로필을 등록한다. 가입하면 지갑이 생긴다.

③ 사이즈 · 상품 추천 (최종: AI 추천) ​

담당 heojungseok(추천) 목적 상품 상세에서 자녀를 고르면 추천 사이즈 · 적합도 · 근거를 보여 주고, 홈의 자녀 맞춤 상품과 상품 상세의 함께 사면 좋은 상품을 자녀 · 장바구니 · 활동 내역으로 추천한다.

카드 그림은 세미의 규칙 추천 기준입니다. 받는 것 · API · 완료 기준은 아래 표가 기준입니다(경로가 /api/v1/recommendations/...로 바뀜).

④ 주문과 결제 ​

담당 L2J92(주문) · codes-gy(결제) 목적 장바구니에 담은 상품을 주문하고 예치금으로 결제한다.

  • 완료 기준 충전하고 주문하면 재고가 줄고, 지갑 잔액이 줄고, 주문이 PAID가 된다. 주문상품에 당시 자녀 정보와 사이즈가 남는다.
  • 처리 순서 가격 확인 → 주문 저장(결제대기) → 재고 차감 → 결제. 화면이 본 단가를 주문 요청에 담아 보내고, 주문 복사본의 현재 단가와 다르면 저장 전에 거절(409)한다. 주문하기 응답은 201 + 주문 상세(결제대기)이고, 결과(PAID · CANCELLED)는 주문 상세나 타임라인으로 확인한다 (P5). 같은 주문을 두 번 만들지 않게 Idempotency-Key 헤더를 보낼 수 있다.
  • 최종 · 받는 것 · 넘기는 것 결제가 주고받는 이벤트는 Kafka(kidly.order.events → 결제 → kidly.payment.events). 판매자 주문상품 취소됨(order-item.cancelled) → 결제: 주문상품 금액만큼 부분 환불 · 상품: 재고 복구. 장바구니 담김(cart.item-added) → (추천 예정)
  • 최종 · 만들 API 공용 장바구니 /api/v1/wishes · 조르기 /api/v1/wish-requests(보내기 · 승인 · 거절, 주문) · 충전 취소 POST /api/v1/wallets/me/charges/{chargeId}/cancel · 입출금 내역 GET /api/v1/wallets/me/ledgers(결제)
  • 최종 · 완료 기준 결제 서비스를 멈췄다 다시 띄워도 그동안 쌓인 결제 요청이 처리되고 주문이 PAID가 된다(Kafka가 메시지를 보관). 자녀가 조르기를 보내면 부모가 승인해 바로 결제할 수 있다.

⑦ 상세 1. 한눈에 (Rough) ​

  1. 주문상품이 구매확정되면 정산 대상 1건이 쌓입니다 (PENDING). 같은 주문상품은 한 번만.
  2. 정산 실행(자동은 영업일 하루 1회 · 수동)이 종료 기준일(자동 = 실행일 0시) 전에 확정된 대상을 판매자별로 묶어 정산서를 1장씩 만듭니다. 대상이 없는 판매자는 정산서를 만들지 않습니다. 수수료는 합계 × 수수료율, 원 미만 버림.
  3. 정산서를 만든 트랜잭션에서 지급 요청을 아웃박스에 저장해 Kafka로 보내고, 결제가 판매자 지갑에 적립한 뒤 결과를 보냅니다. 정산은 결과를 정산서에 반영합니다 (PAID · FAILED).

⑦ 상세 6. 일괄 정산 — Spring Batch ​

Rough 스케줄러 · 관리자 API → settlementJob(종료 기준일) → settleSellerStep: 판매자 ID 읽기 → 판매자마다 정산서 계산 · 저장 · 대상 정산 · 지급 요청 → 결과는 Batch 실행 기록

왜 Spring Batch 판매자 단위로 나눠 처리하고, 한 판매자의 실패를 건너뛰고, 끝난 작업의 재실행을 막고, 실패한 작업을 이어서 다시 돌리는 기능을 직접 만들지 않고 씁니다. 실행 기록도 Batch 메타데이터에 남습니다.

구성내용 (Detail)
작업 파라미터cutoffAt — 작업을 구분하는 값 (같은 기준일 = 같은 작업) · triggerType · requestedBy(자동 실행은 없음) — 구분에 쓰지 않는 값
읽기 (Reader)정산할 판매자 ID: status = 'PENDING' AND confirmed_at < :cutoffAt인 대상의 판매자를 판매자 ID 순으로 페이지 읽기 (seller_id > 마지막 ID 방식이라 처리 중 상태가 바뀌어도 페이지가 밀리지 않음)
쓰기 (Writer)판매자마다: PENDING · 기준일 이전 대상을 읽어 판매금액을 더함(넘침 검사) → Settlement 계산 · 저장 → 대상마다 settle(정산서 ID) → settlement.payout-requested를 아웃박스에 저장. 대상이 없으면 건너뜀. 한 묶음이 한 트랜잭션이고, 커밋된 뒤 릴레이가 Kafka로 보내 결제가 받음
Processor 없음Batch 6은 쓰기에 실패한 묶음을 판매자 1명씩 다시 처리할 때 Processor를 다시 부르지 않고 롤백된 결과를 다시 씀. 그래서 읽기 · 계산을 Writer 안에서 매번 새로 함 (정상 판매자가 함께 건너뛰지 않게)
묶음 크기설정값 (지금 판매자 100명)
실패 처리업무 오류(검증 실패 · 넘침 · 버전 충돌 · 유니크 위반)는 건너뜀(skip). 묶음이 실패하면 Batch가 판매자 1명씩 다시 처리해 실패한 판매자만 건너뜀. 건너뛴 판매자는 ERROR 로그 + 실행 기록 fail_count, 다음 실행에서 다시 대상이 됨 (PENDING 그대로)
중복 실행같은 cutoffAt 작업이 이미 끝났으면 409 (이미 정산한 기준일) · 실행 중이면 409 · 실행 시작 전에 Batch의 실행 중 작업을 조회해 409. 동시에 온 두 요청이 같이 통과해도 정산 대상 @Version · 정산서 유니크가 중복 정산을 막음
다시 실행작업 자체가 실패(FAILED)하면 같은 기준일로 다시 실행. 건너뛴 판매자가 있어도 작업은 완료라 같은 기준일 재실행은 409이고, 남은 대상은 다음 기준일에 정산. 읽기가 PENDING만 고르므로 이미 정산한 판매자는 다시 처리하지 않음 (읽기 위치를 저장하지 않음)
실행 기록따로 저장하지 않음. 실행 결과 · 조회 API는 Batch 작업 실행(ID · 파라미터 · 상태 · 단계 쓰기/건너뛴 수)으로 만듦
자동 실행@Scheduled(cron = 설정값, zone = "Asia/Seoul") (지금 평일 09:05~17:05 매시간) → 영업일인지 확인(주말 · 공휴일이면 건너뜀, 공휴일 조회 실패면 다음 시간 재시도) → 종료 기준일 = 실행일 0시 → 작업 실행 (그날 이미 정산했으면 409로 건너뜀)
수동 실행POST /api/v1/admin/settlements/run → 같은 작업을 끝날 때까지 기다려 실행 (시연용) → 201 + 실행 결과
설정값settlement.fee-rate(0.1) · settlement.run-cron(0 5 9-17 * * MON-FRI) · settlement.payout-retry-cron(0 */10 * * * *) · settlement.chunk-size(100) · spring.batch.job.enabled=false(기동 때 자동 실행 안 함) · spring.batch.jdbc.table-prefix=settlement.BATCH_ · spring.batch.jdbc.initialize-schema: local always, 그 외 never(배포 전 DDL)

보완POST /admin/settlements/{settlementId}/retry지급 결과 복구: 결과를 못 받은 COMPLETED만, 같은 settlementId로 지급 요청 재발행 → 결제가 저장된 결과를 다시 보냄. PAID · FAILED는 409

역할은 경로로 정해집니다: /seller/** = SELLER, /admin/** = ADMIN (아니면 403). 목록이 비면 [].

항목고른 것이유 (다른 선택지)
